完整审稿流程

FULL_REVIEW 更接近真实期刊/会议审稿链路：先解析论文和目标 venue，再由 SE/AE 做编辑筛选，通过后进入四路外审，最后由 AE 汇总成决定信和最终报告。

外审四个角色怎么分工

review_dispatch 不是一个复杂计算节点，它更像分发器。真正生成审稿意见的是下面四个并行节点。

reviewer_reports 使用 Annotated[list, add] 聚合

R1 reviewer1

方法论和实验审稿人。

  • 方法是否清楚
  • 实验和对照是否充分
  • 可复现性是否可靠

R2 reviewer2

领域贡献和相关工作审稿人。

  • 贡献是否真实
  • 与现有工作的差异
  • 是否符合目标 venue

R3 reviewer3

跨学科读者视角。

  • 表达是否清楚
  • 假设是否合理
  • 迁移性和边界条件

D devils_advocate

专门寻找最强反对意见。

  • 攻击核心 claim
  • 找失败案例
  • 提醒 AE 潜在风险

关键分支

完整流程不是永远走到外审。解析失败、内容无效、编辑桌拒都会提前进入输出节点。

doc_parse → parse_fail_output

文件无法解析时，不继续调用后续 LLM 审稿，直接生成解析失败说明。

content_check → invalid_file

上传内容不像论文时，进入无效文件说明，避免把任意内容当论文审。

se_check / ae_check → desk_reject_output

SE 或 AE 判断桌拒时，直接生成正式桌拒意见和改进建议。

prompt、LLM 和产物的完整链路

完整流程里每个智能体节点都遵循同一个模式：节点准备 context，PromptRepository 填模板，LLMRouter 找真实模型，service 落盘。

node function
  → get_review_nodes()
  → ReviewNodes.xxx(...)
  → PromptRepository.render(prompt_name, context)
  → prompts/<prompt_name>.md
  → LLMRouter.complete_json(...)
  → configs/llm.yaml
  → provider base_url/api_key from .env

为什么要这样分层

LangGraph 节点只关心流程和 state。prompt、模型供应商、parser、venue 加载都藏在 runtime 和 infra 里。以后替换模型或 parser，不应该大改 graph。

和 Single 模式的差别

FULL_REVIEW 多出来的是编辑筛选和多角色外审，因此更接近真实审稿，但也更慢、更容易遇到供应商长文本错误。

Single

field_analyst 后直接进入 single_reviewer，一次性生成综合审稿意见。

Quick

跳过 SE/AE 初筛，但保留四路外审和 AE final。

Full

完整走 SE、AE、四路外审、AE final，最重也最真实。
